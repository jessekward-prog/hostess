Pre-flight — read before creating or updating a repo

Does this app comply with Hostess?

Everything here was pulled from Hostess's actual source and from real bugs it caught this month — a Postgres SSL mismatch, a leaked .env, an AI setting that silently stopped taking effect. Check a repo against this before shipping it, not after Hostess rejects the deploy.

§0

Quick checklist

Run down this list before opening a PR or handing a repo to Hostess. Each item links to the full rule.

  • app.yaml exists at repo root with a valid name and port — §1
  • Dockerfile exists at repo root, and the app inside it binds 0.0.0.0, not localhost — §3
  • App boots and stays up with only the vars Hostess provides automatically — no hard crash on missing optional config — §2
  • If postgres: true, the DB pool honors sslmode=disable in DATABASE_URL — §4
  • AI-capable apps use the fleet's env var names (LM_STUDIO_URL etc.) so Hostess finds them with no manifest edits — reference
  • Nothing in Dockerfile, app.yaml, or the entrypoint reads as privilege-escalation or a hardcoded secret to an LLM reviewer — §6
  • Real .gitignore covering node_modules/ and .env — checked, not assumed — §7
§1

app.yaml + Dockerfile

The two files Hostess refuses to deploy without. manifest.js validates both before a build ever starts.

app.yaml at repo root

Required

name and port are required; everything else is optional:

name: my-app          # ^[a-z0-9][a-z0-9-]{0,48}[a-z0-9]$ — 2-50 chars
port: 3000             # container-internal port the app listens on
postgres: false         # optional, default false — see §4
env:                   # optional — see §5, mostly unnecessary now (auto-detected)
  - SOME_VAR
dataDir: /app/data      # optional, absolute container path — see below
autoUpdate: false        # optional, default false — see below
description: "..."       # optional, cosmetic — see below
icon: public/icon.png    # optional, cosmetic — see below

Why port trips people up: it's the port your process binds to inside the container, not the host port you'll browse to — Hostess picks that automatically from 4000–4999 and remaps it for you.

dataDir — persistent storage outside Postgres

Optional

An absolute path inside the container. Hostess mounts a named Docker volume there (survives redeploys/restarts, same as the bundled Postgres does) — for uploads, SQLite files, or any other on-disk state that isn't in the database.

autoUpdate — pull and rebuild automatically

Optional

If true and the app was deployed from a git remote, Hostess pulls and rebuilds on its own rather than waiting for a manual redeploy click.

description / icon — dashboard card cosmetics

Optional

Cosmetic only — never blocks a deploy. description is a short blurb (truncated to 200 chars); icon is a path to an image file that must already exist in the repo (checked at deploy time — a bad path is silently treated as unset). Leave either out and the card falls back to a generic avatar and a "scrape" button.

Dockerfile at repo root

Required

Anything that builds and results in a process listening on port. No other constraint on the build itself.

§2

Boot without every var set

First deploy only gets what postgres: true provides automatically. Everything else — API keys, an AI link, optional integrations — gets filled in after the container is already running, from the dashboard's env panel. If your app hard-crashes without them, the operator can never reach the panel that would fix it.

Treat missing optional config as "not configured," not fatal

Required

Gate the boot-time check to only what's truly load-bearing (a database URL, say). Anything optional should leave the feature disabled and the server running:

// Wrong — traps you outside the panel that would fix it
if (!process.env.ANTHROPIC_API_KEY) process.exit(1);

// Right — server boots either way, the feature just reports its own state
const anthropic = process.env.ANTHROPIC_API_KEY ? new Anthropic({ apiKey: ... }) : null;

Hit for real in macro-cmd: it exited immediately whenever ANTHROPIC_API_KEY was unset, even when a local model was the intended provider — the fix that unblocked it was exactly this pattern.

§3

Networking

Hostess maps 127.0.0.1:<hostPort> on the host to <containerPort> inside the container — loopback only, never LAN or internet-reachable through Hostess itself.

Bind 0.0.0.0 inside the container

Required

Binding to 127.0.0.1 or localhost inside the container makes the app unreachable from the host — the loopback restriction is applied by Hostess's own docker run -p, one layer out. Your process should listen as broadly as its framework's default usually already does.

Don't assume public reachability

Recommended

If a deployed app needs to be reachable beyond the host, that's a separate reverse-proxy/tunnel decision the operator makes — not something the app itself should assume or configure around.

Need a public link for one narrow thing? Declare it, don't self-tunnel

Recommended

An app that stays private (no Go Online, Tailscale-only) but still needs to hand out a public download/share link should never bundle a tunneling binary or spawn its own outbound tunnel — that's exactly the capability the previous rule says the app doesn't get to assume for itself, and an AI security scan can't reliably tell a legitimate reason from a claimed one in a code comment. Declare a second, narrow port instead:

# app.yaml
publicGateway:
  port: 3001   # a second internal listener, separate from the main port

That port should carry only the specific public routes (e.g. a token-gated file download) — no login, no listing, no upload, nothing else the main app exposes. Hostess maps a second host port for it and owns the tunnel lifecycle entirely (per-app card gets an "Allow sharing features" toggle); the app itself never runs cloudflared or anything like it. To learn its own current public URL, the app reads a file Hostess writes read-only into the container at /run/hostess-gateway/url — empty or absent when the toggle is off — rather than querying any API. This keeps the actual capability (can this container reach the internet on its own initiative) entirely off the app and on the trusted platform, where a redeploy security scan can inspect it as static config instead of trusting what the code claims to do.

Built for cmd-drive's per-file share links (2026-09-05): the app declares publicGateway.port, Hostess's lib/gateway.js + lib/tunnel.js own the Quick Tunnel (including auto-reconnect if it drops — free tunnels have no uptime guarantee), and share-link generation reads the handoff file live at share-time rather than caching a URL. The same pattern generalizes to any app that currently hard-codes a public domain (a Coolify/Railway deployment, say) purely so one feature can hand out a link — this gives it a Hostess-native way to do the same thing without ever holding the tunnel capability itself.

§4

Postgres

Set postgres: true and Hostess provisions a database + role in its shared postgres:16-alpine container, injecting both a connection string and discrete fields.

VarWhat it is
DATABASE_URLFull connection string, ?sslmode=disable appended — see below
DB_HOST / DB_PORT / DB_NAME / DB_USER / DB_PASSWORDThe same connection, split — for apps that don't parse a URL

Honor sslmode=disable — don't force SSL from NODE_ENV alone

Required

The bundled Postgres doesn't speak TLS at all. A very common pattern silently breaks against it:

// Breaks here: ignores the connection string, forces SSL whenever NODE_ENV=production
ssl: process.env.NODE_ENV === 'production' ? { rejectUnauthorized: false } : false

// Correct — the connection string's own sslmode wins
ssl: /sslmode=disable/i.test(process.env.DATABASE_URL || '')
  ? false
  : process.env.NODE_ENV === 'production' ? { rejectUnauthorized: false } : false

Hit for real in macro-cmd — booted fine everywhere else, then failed exactly this way the first time it was deployed through Hostess. Now fixed at the source (Hostess appends sslmode=disable) and the app should still check for it, since the same code often also runs against a real TLS-requiring Postgres elsewhere (Coolify, Railway).

Redeploys reuse the same database

Good to know

Same role, same password, same data — not a fresh instance each time. Don't write migrations or seed logic that assumes a clean slate on every deploy.

§5

AI / local model link

Two tiers. Tier 1 costs nothing — just use the right names. Tier 2 gets you a live model picker and Local/Claude toggle on the app's Hostess card, editable with no redeploy.

Tier 1 — use the fleet's env var names

Auto-detected

Every deploy scans the repo's own .js/.mjs/.cjs/.ts files for these names and adds any it finds to the env panel — no app.yaml edit required, ever:

VarPurpose
LM_STUDIO_URLLocal model endpoint, e.g. http://100.x.x.x:1235
LM_STUDIO_API_KEYBearer key the local endpoint requires
LM_STUDIO_MODELModel id to request
ANTHROPIC_API_KEYClaude, if the app supports it as a second provider
VISION_PROVIDERlocal or anthropic — which one unattended calls default to
SYNC_SECRETOnly needed for Tier 2 — see below

Tier 2 — implement GET/PUT /api/lm

Recommended for AI-capable apps

Full contract is in the reference section below. In short: report your current connection state, accept live updates to it, persist them somewhere that survives a restart, and gate the routes so a trusted machine (not just a logged-in person) can call them.

Already deployed? Redeploy after adding it

Required

Hostess builds the image once, at deploy time. Adding /api/lm to an app that's already running here doesn't touch the live container — the card will show ai-link as unreachable (a 404 probe) until you hit redeploy to rebuild from the new commit. Not a bug, just easy to forget mid-change.

Never invent your own SYNC_SECRET

Required if using Tier 2

Declare it as an env var your app reads — Hostess auto-generates and injects a random value the first time it's deployed, the same way it already does for Postgres passwords. No one should ever type or paste one.

const SYNC_SECRET = process.env.SYNC_SECRET || '';

function authOrSync(req, res, next) {
  if (SYNC_SECRET && req.headers['x-sync-secret'] === SYNC_SECRET) return next();
  return requireAuth(req, res, next); // your normal user auth, as a fallback
}

Collision safety: generated fresh, locally, per install — crypto.randomBytes(16), 128 bits of entropy. Two installs never converge on the same value, and it's never committed (Hostess's registry.json is gitignored).

§6

Security guard

Before every build, a local LLM reads Dockerfile, app.yaml, and the guessed entrypoint file. risk: high blocks the deploy outright.

What gets flagged

Know before you ship

Hardcoded secrets or credentials in source; curl-pipe-to-shell in the Dockerfile; requests for privileged mode, the Docker socket, or host networking; unauthenticated command-execution endpoints; obfuscated code; anything that scans the local network.

Hostess's own docker run never grants privileged/socket/host-network access regardless of what's asked for — so a Dockerfile requesting it reads purely as suspicious intent to the guard, with no functional upside.

Keep secrets in env vars, never literals

Required

A hardcoded API key or password in source is both a guard trigger and a real leak if the repo is ever made public.

§7

Repo hygiene

Not enforced by Hostess itself — caught by hand, repeatedly, across real repos this session.

A real .gitignore, checked not assumed

Required

At minimum:

node_modules/
.env
dist/

Found a repo this session with no .gitignore at all — real database credentials in .env sitting one git add -A away from a public commit.

Ref

/api/lm contract

The shape Hostess's ai-link sync (and any app's own settings panel) reads and writes. Implemented today by macro-cmd (dual-provider) and gains-cmd (local only).

GET /api/lm

{
  "provider": "local",                    // which one unattended calls use
  "local": {
    "url": "http://100.x.x.x:1235",
    "model": "google/gemma-4-e2b",
    "apiKeySet": true,
    "models": ["..."],           // live list from the endpoint's /v1/models
    "error": null                 // set if the endpoint's own connection failed
  },
  "anthropic": {                     // omit this whole key if Claude isn't an option at all —
    "apiKeySet": false,             // don't report a permanently-false key for "not supported"
    "model": "claude-sonnet-4-6"
  },
  "managedEnv": ["LM_STUDIO_URL", "LM_STUDIO_API_KEY", "LM_STUDIO_MODEL"]
}

managedEnv is what stops the raw env panel and ai-link from double-offering the same field — list every var this endpoint makes live-editable, and the caller hides those from its generic env list automatically. No hardcoded naming convention to keep in sync on the Hostess side.

PUT /api/lm

{
  "url": "...",              // any subset — omitted fields are left unchanged
  "apiKey": "...",
  "model": "...",
  "provider": "local" | "anthropic",
  "anthropicApiKey": "..."
}

Persist to a small key/value settings table (env vars are only the initial seed), reload the live in-process values immediately — no restart — and return the same shape as GET.

Auth

Accept your app's normal user auth or the x-sync-secret header — see §5's authOrSync pattern. Never leave these routes fully unauthenticated; several apps in this fleet are publicly reachable, not just loopback-local.
